# Bootstrap

Reproducible-from-scratch runbook for bringing up HoneyCow on a fresh
abuse-tolerant VPS. Captures every non-vanilla touch the running host
needs — everything not listed below is stock Ubuntu 24.04 cloud image.

For ongoing operation (logs, exemption reload, deploy iteration) see
`deployment.md`. For wire-protocol invariants see `architecture.md`.

## Prerequisites

- A VPS with:
  - Public IPv4 (and ideally IPv6) — DNS clients route to literal
    addresses, so the host needs to own its addresses
  - UDP and TCP `:53`, TCP `:80`, TCP `:443` reachable from the
    internet
  - An abuse-tolerant provider (this thing intentionally attracts
    attention)
  - At least 1 GB RAM and 25 GB disk; HoneyCow itself is small but log
    volume grows
- Ubuntu 24.04 LTS cloud image with the default non-root sudo user and
  the operator's SSH key already injected (the cloud-init default —
  no extra step needed)
- A domain you control delegated to authoritative nameservers somewhere
  you can issue dynamic updates to via TSIG (used for DNS-01 cert
  issuance). HoneyCow does not issue or serve your real zone — see the
  `## Registrar Delegation` section of `deployment.md` for the parent
  zone you set up out-of-band.

## Host preparation

The host needs four non-default touches before HoneyCow can run.

### 1. Free port 53 from systemd-resolved

Ubuntu's `systemd-resolved` binds `127.0.0.53:53` by default. Disable
the stub listener so the HoneyCow container can publish `:53`:

```bash
sudo mkdir -p /etc/systemd/resolved.conf.d
printf '[Resolve]\nDNSStubListener=no\n' \
  | sudo tee /etc/systemd/resolved.conf.d/disable-stub.conf
sudo systemctl restart systemd-resolved
```

`/etc/resolv.conf` will continue to resolve via the upstream resolvers
your cloud provider injected; the only thing that changes is that no
process is bound to `:53` locally.

### 2. (Optional) Add swap

The committed memory limit on the honey-ns container is 256 MB, but the
acme + Caddy sidecars and the kernel itself can spike during cert
renewals. 1 GB of swap is cheap insurance:

```bash
sudo fallocate -l 1G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 3. (Optional) Set timezone

Default is UTC. Operator preference if not.

```bash
sudo timedatectl set-timezone America/Chicago
```

### 4. SSH hardening

Cloud-init's defaults already disable password auth. Add a drop-in
that also disables root login and is explicit about pubkey:

```bash
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
EOF
sudo systemctl restart ssh
```

## Docker install

Use Docker's official `apt` repo, not the distro package (the distro
package lags too far):

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
  https://download.docker.com/linux/ubuntu noble stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker "$USER"   # log out / back in for group to apply
```

Add log rotation to the daemon config so containers don't fill the
disk:

```bash
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
EOF
sudo systemctl restart docker
```

## Code

Drop the repo at `~/projects/honeycow` (any path works — adjust the
compose commands accordingly):

```bash
mkdir -p ~/projects
# Either: git clone <your remote> ~/projects/honeycow
# Or:     rsync the repo from your dev machine to ~/projects/honeycow
```

Create `~/projects/honeycow/.env` from `.env.example` and fill in the
host-specific values (public IPv4/IPv6, NS hostnames, abuse email,
calling card, etc). `.env` is gitignored — see
`feedback_parameterize_deploys` for the rationale.

## TLS / ACME prerequisites

The Caddy overlay uses an `acme.sh` sidecar that proves domain control
via DNS-01 against a BIND nameserver you (or your DNS operator)
control. Two things have to exist before first-cert issue:

1. **A BIND nameserver authoritative for your domain that accepts
   TSIG-signed nsupdate calls.** Setup is out of scope here — see
   BIND's `tsig-keygen` + `update-policy` docs.

2. **A TSIG key file at `~/projects/honeycow/acme/tsig.key`** in
   `nsupdate` format, generated by whoever runs the authoritative
   nameserver:

   ```
   key "acme-update." {
     algorithm hmac-sha256;
     secret "<base64-secret>";
   };
   ```

   Permissions: `chmod 600 acme/tsig.key`. The file is gitignored.

Then set `ACME_NSUPDATE_SERVER` and `ACME_NSUPDATE_ZONE` in `.env` to
point at the BIND host and the zone the key is authorized for.

## First-time cert issuance

The one-time commands live as a comment block at the top of
`docker-compose.prod.yml`. In short:

```bash
cd ~/projects/honeycow
export $(grep -v '^#' .env | xargs)

# Build the local image first so the daemon won't complain about a
# missing image when other services start.
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  build honey-ns

# Register an LE account, issue, install the cert into /certs.
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm acme --register-account -m "$HONEY_ABUSE_EMAIL"
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm acme --issue --dns dns_nsupdate -d "$HONEY_DOMAIN" \
  --server letsencrypt
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm acme --install-cert -d "$HONEY_DOMAIN" \
  --fullchain-file /certs/$HONEY_DOMAIN/fullchain.pem \
  --key-file /certs/$HONEY_DOMAIN/privkey.pem \
  --reloadcmd 'wget -q -O- --post-data="" http://caddy:2019/load || true'
```

(`$HONEY_DOMAIN` is the bare domain without trailing dot when used as a
filesystem path; check what `.env` looks like.)

## Bring up the stack

```bash
cd ~/projects/honeycow
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
```

Three containers should be `running`: `honeycow`, `honeycow-caddy`,
`honeycow-acme`.

## Firewall: UFW + ufw-docker

By default Docker bypasses UFW on IPv4 via its own `iptables` rules,
which means the host's UFW is decorative for any container-published
port. `ufw-docker` (chaifeng/ufw-docker) closes that gap by routing
container ingress through a UFW-visible chain, which also makes UFW
logging actually capture wire-level probes for correlation with
HoneyCow's own event log.

```bash
sudo curl -fsSL -o /usr/local/bin/ufw-docker \
  https://github.com/chaifeng/ufw-docker/raw/master/ufw-docker
sudo chmod +x /usr/local/bin/ufw-docker
sudo /usr/local/bin/ufw-docker install
```

`ufw-docker install` rewrites `/etc/ufw/after.rules` to deny external
→ container traffic by default — you must restate every exposed port
as a route rule, **before** restarting UFW, or external probes will
get black-holed:

```bash
sudo ufw allow 22/tcp comment 'SSH'
sudo ufw route allow proto udp from any to any port 53 comment 'honeycow DNS UDP'
sudo ufw route allow proto tcp from any to any port 53 comment 'honeycow DNS TCP'
sudo ufw route allow proto tcp from any to any port 80 comment 'honeycow HTTP'
sudo ufw route allow proto tcp from any to any port 443 comment 'honeycow HTTPS'
sudo systemctl restart ufw
sudo ufw enable
sudo ufw logging medium
```

`medium` rate-limits kernel-side; logs land at `/var/log/ufw.log` and
rotate weekly via the distro's default `/etc/logrotate.d/ufw`.

## Verification

```bash
# Local self-checks
make smoke HOST=127.0.0.1

# External checks — replace VPS_IP with your host's public address
VPS_IP=$(curl -s ifconfig.me)
dig @$VPS_IP A target.example.com               # synthesized sinkhole A
dig @$VPS_IP SOA random.tld                     # synthesized SOA
dig @$VPS_IP AXFR example.com | grep REFUSED    # zone transfer refused
curl -sI http://$VPS_IP/                        # HTTP closer
curl -sI https://$HONEY_DOMAIN/                  # Caddy explainer
```

## What this leaves on the host

Files / directories created by this runbook:

- `/etc/systemd/resolved.conf.d/disable-stub.conf`
- `/etc/docker/daemon.json` (log rotation)
- `/etc/ssh/sshd_config.d/99-hardening.conf`
- `/usr/local/bin/ufw-docker`
- `/etc/ufw/after.rules` and `/etc/ufw/after6.rules` (modified in
  place by `ufw-docker install`; pre-modification copies saved with a
  `~timestamp~` suffix automatically)
- `~/projects/honeycow/` (the repo)
- `~/projects/honeycow/.env` (gitignored)
- `~/projects/honeycow/acme/tsig.key` (gitignored, mode 600)
- `/swapfile` (if you took the optional step)
- Docker named volumes: `honeycow_logs`, `caddy_data`, `caddy_config`,
  `caddy_certs`, `acme_data`

Removing all of those plus the docker apt repo + docker packages
returns the host to vanilla.
