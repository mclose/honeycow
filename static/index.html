You reached this page because something on your network resolved a hostname whose DNS answer pointed at our IP, then connected to it over HTTP. Most often that means a scanner or misbehaving client queried this DNS server expecting a real authoritative response.

Honeycow is a deliberately incorrect DNS server — an NS squatter that synthesizes plausible-looking answers for any name in any zone. We do not own the domains we reply about. The IP your client connected to is ours; the records that pointed it here are fabricated.

How honeycow is observably not an open resolver

If you arrived here from a Shadowserver / Censys / etc. report flagging this IP as an open resolver, these are the wire-level properties you can verify with dig:

  • Authoritative-claiming, not recursive. Every response sets AA=1 and clears RA=0 (recursion not available). Honeycow never forwards a query.
  • No EDNS. Responses omit the OPT pseudo-RR. Clients advertising larger buffer sizes are ignored.
  • 512-byte UDP cap with TC=1. Anything that would exceed 512 bytes truncates with empty answer / authority / additional sections, forcing TCP retry. Removes the spoofed-UDP amplification path.
  • Per-source UDP rate limiting via token bucket. Burst-tolerant; sustained source floods are dropped.
  • AXFR / IXFR → REFUSED in every case.
  • Reserved-zone refusal. Names defined by RFC 6761 / 2606 / 6303 / 4193 (.localhost, example.com, the RFC 1918 reverse zones, etc.) return REFUSED instead of synthesized records.
  • Research-scanner zones → REFUSED. Names under shadowserver.org, cybergreen.net, internet-measurement.com, internet-census.org, and similar published research-scanner zones are exempt by design — we don't want to falsely validate amplifier paths in their open-resolver reports.

Verify yourself

The truncation behavior is reproducible with one dig against this host. The qname below is a 240-character literal of increasingly enthusiastic moos — no shell expansion, no piped commands, the only "trick" is that it's long enough to push the response over 512 bytes. 

dig +ignore @this-host TXT \
"Mooooooooooooooooooooooooooooooooooooooooooooooooooooooooooo.\
Mooooooooooooooooooooooooooooooooooooooooooooooooooooooooooo.\
Mooooooooooooooooooooooooooooooooooooooooooooooooooooooooooo.\
Mooooooooooooooooooooooooooooooooooooooooooooooooooooooooooo.tld"

The response header should read flags: qr aa tc rd (AA=1, TC=1, RA absent), with ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 0, and dig's annotation recursion requested but not available. +ignore tells dig not to retry over TCP after seeing TC=1, so the truncated UDP response stays visible instead of being immediately replaced by the full TCP answer.
